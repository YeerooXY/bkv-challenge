# Live line and plate search, 2026-11-16

Problem: catalog search filters line IDs or plates only, with additional mode/model/rarity/completion filters. Searching 225 in Plates cannot find vehicles by their active line. Previous vehicle status scraped WinMenetrend in native Android only and did not supply coordinates or direction in browsers.

Implemented an explicit Find live vehicles action on both existing search screens. Enter submits too. Known line numbers resolve via the existing route index; other input queries plates (minimum three plate characters). Catalog filters remain independent. Catalog empty copy now identifies a filter mismatch. Plate details reuse the same lookup; the external vehicle-history link remains available. Live result details show line, destination, last report time, reported stop when supplied, and the existing map component for observed positions. This is a current-report lookup, not a complete historical shift roster; earlier history is linked externally.

Backend reuses Transit._call, _cached, request budget, fixed-host adapter and HTTP origin/rate guards. Added only vehicles-for-route and vehicles-for-location as allowlisted endpoints; no full feed, polling, new dependency or database. Up to six route variants, 20-second shared cache, at most 100 returned vehicles with partial flag if truncated. Plate query uses a fixed Budapest-area bounding box and normalized query; no caller-controlled upstream URLs/coordinates. No request occurs on each keystroke or automatically when opening a catalog item.

41 Python and 15 Node tests passed. tests/browser/live-search.cjs passed PC Chromium, desktop WebKit, Android Chromium and iPhone WebKit: both search screens, route/plate results, no keystroke requests, vehicle marker, destination, Space/Enter/Tab/Shift+Tab/Escape, restored focus, error/retry and empty states, and no document overflow. All four screenshots were inspected. Map tiles are synthetic in this deterministic UI check; live tile imagery and physical devices were not verified. Actual Safari/native Android rendering remains untested.

Deployed server.py, futar.py and routes.json to the existing VM service and restarted only bkv-api. Live private HTTPS lookup for 225 returned AAHY805, MFW522 and SKR806, all with fresh reports. SKR806 lookup returned line 225, toward Mexikoi ut M, with coordinates. Pages-origin CORS passed. The line response body was 874 bytes before connection overhead; maps add separate tile traffic. No credentials, Tailscale routes or FamilyHub services were changed. Backend copies retain .previous rollback files. Website service-worker cache v24.
